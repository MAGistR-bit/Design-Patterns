### 👨‍💻 Заметки к главе №1.
Каждая утка **СОДЕРЖИТ** 
экземпляры `FlyBehavior`, `QuackBehavior`,
которым делегируется выполнение соответствующих
операций.

Подобные связи между классами означают, что
вы используете **механизм композиции**.

**Принципы проектирования:**
> 1. Инкапсулируйте то, что изменяется.
> 2. Отдавайте предпочтение композиции перед
> наследованием.
> 3. Программируйте на уровне интерфейсов, а не реализации.
> 4. Стремитесь к слабой связанности взаимодействующих объектов.

**Концепции ООП:**
> 1. Абстракция
> 2. Инкапсуляция
> 3. Полиморфизм
> 4. Наследование

Композиция используется во многих паттернах
проектирования.

> Паттерны не придумывают - их находят.

> Паттерны содержат проверенный опыт ОО-проектирования.

### 💡 Цель
Определить, какие аспекты приложения 
отличаются друг от друга, и отделить их от тех,
что остаются неизменными.
Так, например, у всех уток есть некоторые
общие свойства. Но некоторые утки могут 
летать, а некоторые (например, пекинская утка) нет, и некоторые утки могут крякать, 
а некоторые нет (например, резиновая утка).

Мы знаем, что `fly()` и `quack()` являются
частями класса `Duck`.
Чтобы отделить эти методы от класса `Duck`,
нужно извлечь эти методы из класса `Duck`
и создать новый набор классов 
для представления каждого поведения (behavior).

### ❗ Зачем?
Это позволяет не писать повторяющийся код 
для всего приложения. 

Конечно, может быть один огромный класс `Duck`,
который использует `fly()` и `quack()`, но 
это будет означать, что для нелетающих уток 
придется переопределить эти методы
и оставить их пустыми, что приведет 
к большому количеству повторяющегося и 
мертвого кода повсюду.

Это решение позволит вносить 
менее радикальные изменения в приложение.

Если изменить или добавить новое поведение
в класс `Duck`, придется редактировать
все места, где класс `Duck` использовался
в приложении, что приведет ко многим 
новым изменениям / возможности появления
новых ошибок.

Использование паттерна позволит динамически изменять 
поведение утки во время выполнения программы.
---

### ✏️ Решение
- Поведения (Behaviors): FlyBehavior, QuackBehavior.
- Эти поведения могут стать интерфейсами, 
поскольку они являются переменными свойствами,
как описано выше.
- Интерфейс **FlyBehavior** будет иметь метод `fly()`.
- Интерфейс **QuackBehavior** будет иметь метод `quack()`.

Класс `Duck` становится абстрактным классом 
и объявляет две ссылочные переменные (reference variables),
`QuackBehavior` и `FlyBehavior`.

Абстрактный класс `Duck` также делегирует
поведение `fly` и `quack`.

```java
import ducks.behavior.fly.FlyBehavior;
import ducks.behavior.quack.QuackBehavior;

abstract class Duck {
    FlyBehavior flyBehavior;
    QuackBehavior quackBehavior;

    public Duck() {
        
    }
    
    void performFly() {
        flyBehavior.fly();
    }

    void performQuack() {
        quackBehavior.quack();
    }

    void setFlyBehavior(FlyBehavior fb) {
        flyBehavior = fb;
    }

    void setQuackBehavior(QuackBehavior qb) {
        quackBehavior = qb;
    }
}
```

В этом главе используется паттерн "Стратегия".  
**Академическое определение:**
> **Паттерн Стратегия** определяет семейство алгоритмов,
> инкапсулирует каждый из них и обеспечивает
> их взаимозаменяемость. Он позволяет
> модифицировать алгоритмы независимо от их
> использования на стороне клиента.
